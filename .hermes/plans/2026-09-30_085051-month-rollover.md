# Audit site month rollover implementation plan

> **For Hermes:** Implement after Kit approves, with focused tests before each change. Do not modify patient records.

**Goal:** At the September→October boundary, open the new fiscal year (ปีงบประมาณ 2570), retain September/FY2569 history, and reset October's current-month metrics without losing cumulative tracking.

**Architecture:** Derive one explicit `report_period(today)` in Asia/Bangkok and use it for all current-period calculations and labels. Because October starts a new fiscal year, **show October / FY2570 from Oct 1** with a clear "ยังไม่มีข้อมูลสิ้นสุดวัน" empty state instead of `วันที่ 1–0`; from Oct 2 show Oct 1 cases. September/FY2569 remains selectable as history. Historical tracking remains keyed by surgery month (Buddhist `YYYY-MM`), with a separate computed fiscal-year key (Oct–Sep); never reset historical files.

**Tech stack:** Python stdlib + static HTML/JS, Google Sheets source, GitHub Pages; no new dependencies or new cron.

## Findings from current code
- `~/.hermes/scripts/register_site_update.py` (same file as symlink `~/register-system/register_site_update.py`) uses `day_to = t.day - 1` and fixes the month to `t.month`: on Oct 1 it computes October `1–0`, zeroes dashboard metrics and renders a nonsensical header. The previous-month trend currently compares against September, which is wrong if September itself becomes the active display period.
- `all_cases`, `month_options`, and `daily_by_month` currently include finished cases dated **today**, while `month.cases`, `finished_by_month` and dashboard metrics exclude today. Thus dropdown/table/graph/progress can diverge on the 1st and throughout any month.
- `~/audit-orwnh.reg-new/build_html.py:137` picks `month_options[0]`, i.e. newest date found in the sheet, rather than the period selected by the server. An October row can make October selected while the page header/summary still refer to September.
- `~/register-system/register_gsheet_report.py:42-43,113` returns zero and writes `วันที่ 1–0` on the 1st. This is a separate daily report, not automatically fixed by the audit-site change.
- `missing_history.json` and `ever_seen.json` already hold entries by surgery month; they should **not** be cleared at rollover. `first_seen.json` should retain only still-pending cases even across months.

## Tasks

Implement importable `report_period(today)` in `register_site_update.py`; make it return `(month_key, fiscal_year, start, end_or_none)` without fetching Google data. Run `python3 -m unittest discover -s tests -v` and verify fail→pass.

On Oct 1 show October zeros/empty state and October-only cumulative top fields (initially none); Sep remains visible via dropdown. On Oct 2 show October totals. Compare `insights.finished_total` to selected `month_progress[period_key]['total']`; trend compares October to September but shows "รอข้อมูล" rather than misleading percentage on Oct 1.

Unit-test Oct 1 fixture with Sep 30 and Oct 1 cases, then Oct 2 admitting Oct 1. ## Risks and decisions
- **Updated recommendation after Kit's fiscal-year note:** Start October/FY2570 on Oct 1, showing a truthful empty state until Oct 2; keep September/FY2569 in the dropdown. This supersedes the earlier recommendation to display September as the default on Oct 1. Confirm this presentation choice before implementation if FY-year switching on Oct 1 is not desired.
- The website and GSheet report have independent logic. Changing one alone leaves inconsistent dates on Oct 1; keep rules synchronized.
- No Sheet row edits, patient record deletion, tracking reset, or permission changes. Historical public JSON still contains HN/name under the existing approved audit-page scope; do not create a new public destination.
